What was actually inspected

All four metadata CSV files were read in full. The tracking folder contains 122 files (about 850 MB); two were read in full for this audit: Tampa Bay–Dallas on 9 September and Indianapolis–Tennessee on 31 October. Tracking findings apply to these 181 plays, not an unperformed audit of every game.

pffScoutingData.csv188,254 rows22 player records per play: role, lineup position, credited hits/hurries/sacks, blocker outcomes and first blocked defender.
Two tracking files175,007 rows / 7,609 frames22 players plus the ball in every sampled frame. Position, speed, acceleration, movement direction and events.

The full play table has 4,620 C, 2,755 I, 543 S, 190 IN and 449 R records. These are raw dataset labels, not official totals: 489 descriptions contain “No Play.” The full scouting table has labels on 793 distinct plays for a hit, 2,323 for a hurry and 536 for a sack; categories can overlap and do not perfectly equal outcome counts.

  • Game/play/player join keys are unique, and all sampled player rows match names and scouting roles.
  • Sample tracking has 181 snap markers, 170 release markers, one catch marker and no tackle markers. There are 101 completed-pass outcomes, showing why an outcome label cannot be treated as a recorded catch frame.
  • Timing: exported timestamps have whole-second precision. Use (frameId − snapFrame) / 10 for seconds, based on the NFL's 10 Hz tracking rate.
  • PFF roles use values such as Pass Route, Pass Rush and Pass Block. Normalize case; do not assume the README's capitalization exactly matches the CSV.
  • Null values in scouting fields often mean the field does not apply to that player's role. Treat a missing measurement differently from a genuine zero.

The smallest useful build

Use one field replay with three optional layers: receiver spacing, quarterback-to-rusher distance, and recorded play context. Both the private controller and the audience output should read the same play/frame state. Only the creator chooses what to publish.

  1. Load a play. Join plays and games on gameId; join scouting on gameId + playId + nflId; join names on nflId. A frame is gameId + playId + frameId. Never join on playId alone.
  2. Build the field. Raw x runs from 0 to 120 including end zones. Goal lines are x=10 and x=110. Draw the line of scrimmage from absoluteYardlineNumber and the target using playDirection and yardsToGo. If rotating a left-going play, transform every entity, line and orientation consistently.
  3. Compute spacing. For a route runner R and defenders D in the same frame, calculate min(sqrt((Rx−Dx)^2 + (Ry−Dy)^2)). Preserve the nearest defender ID as well as distance. Require complete opposing-player coverage or show unavailable.
  4. Compute timing. Prefer ball_snap and pass_forward. In this sample, automated pass-forward tags can differ from the annotated tag. Missing or ambiguous release means unavailable. Snap-to-sack is a separate metric.
  5. Compute approach distance. Select the passer using PFF's Pass role and candidates using Pass Rush. Measure distances to the current QB position, not the start line. Preserve which rusher is nearest.
  6. Add recorded context. Show down, distance, game clock, formation and coverage. Keep post-play outcome/pressure credit in an explicitly retrospective reveal, rather than presenting it as a real-time prediction.
  7. Give the creator controls. Select a play/player, play/pause, scrub, jump to snap/release/sack, toggle trails, preview privately, publish and clear. Viewers have no controls.
  8. Prepare two stories. Use the Gronkowski separation example and Wentz sack example. Finish with a screenshot and a short README explaining the measured quantities and the pre-release data limitation.

Prepared handoff files

The two JSON files contain actual frame positions, player names, roles, gap calculations and recorded scouting context. The Python builder reproduces them from the CSVs and supports other play IDs.

  • Gronkowski play data
  • Wentz sack data
  • Reusable Python data builder (requires pandas)
  • All 45 feature specifications as JSON
python build_overlay_data.py --data-dir data --game 2021090900 --play 3793 --out gronkowski-play.json
python build_overlay_data.py --data-dir data --game 2021103106 --play 1231 --out wentz-sack.json

The builder accepts the repository's data/tracking/tracking_GAMEID.csv layout. It returns raw field coordinates and attackDirection. Missing values are JSON null. It checks duplicate entities and unique join keys, exposes incomplete frames, and flags descriptions containing “No Play” for review.

What to leave out of this hackathon version

Do not add catch probability, expected yards, live blitz predictions, automatic blown-coverage blame, full-drive summaries, running-back analysis or fourth-down advice using this data alone. Do not fabricate frames after the recording ends. A 2D field replay does not require video alignment; a camera-anchored overlay would additionally need footage, timing synchronization and camera calibration.
